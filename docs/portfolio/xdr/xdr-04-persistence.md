# XDR-04 | 지속성 공격 탐지

**작업 범위:** 제작 1 — Wazuh 경보 읽기 · 제작 2 — MITRE ATT&CK 패턴 · 제작 3 — 독립 판단 · 제작 4 — 임시 거부 후보·알림 연결 · 제작 5 — 재판정·오차단 확인 (2026-11-07)

**기록 출처:** [XDR 입력 계약](../../../xdr/README.md), [모의 Wazuh 경보](../../../xdr/fixtures/persistence.json), 제작 1~5 소스·재실행 결과, 사용자 제공 공식 심판 판정 (평가 커밋 [`b4a69c2`](https://github.com/Taetaeeee/choi-bujang-secret-vault/commit/b4a69c27248d61b387b1a5be17bb1278e8ca14d1))

**상태:** 제작 1~5와 저장점 완료. 모의 경보 **24건: block 8 / alert 8 / record 8**, 정상 이벤트 오차단 **0건**. 사용자 제공 공식 심판 결과 **필수 조건 4/4, 완결성 가점 3개, 완성도 100/100점, 작전 점수 100/100점**.

## 과제 목표

Windows 서비스를 새로 등록하거나 변경하고, 예약 작업이나 시작 폴더에 프로그램을 심어 시스템을 다시 켜도 실행되게 만드는 **지속성(Persistence) 징후**를 교육용 Wazuh 경보에서 구분합니다. 정상적인 수업 도구·업데이트·예약 작업과 의심스러운 변경을 혼동하지 않도록 탐지와 대응을 분리합니다.

## 제작 1 — 경보 읽기

- **문제:** 원본 경보를 그대로 출력하면 불필요한 정보와 비밀값처럼 보이는 문자열이 섞일 수 있습니다.
- **해결:** `xdr/persistence/read-alerts.mjs`에서 시각, 출발 IP, 계정, 규칙 수준, 설명의 **다섯 필드**만 추출했습니다. 설명에는 비밀번호·토큰 형태를 가리는 처리를 적용하고, 원본 경보를 수정하지 않도록 읽기 모듈을 분리했습니다.
- **검증:** 사용자 PC에서 읽기 모듈 문법을 검사하고 원본 **24건과 출력 24줄**의 일치, 다섯 필드 구조, 비밀값 마스킹, 원본 불변을 확인했습니다. 해당 모듈은 `decide.mjs`에서 불러오지 않습니다.

## 제작 2 — 근거가 있는 탐지 패턴

- **문제:** 서비스·예약 작업·시작 폴더가 변경됐다는 사실 하나만으로 공격을 확정하면 정상 사용자를 막을 수 있습니다.
- **해결:** `patterns.json`에 **서명 없는 새 서비스 등록·실행 파일 변경**, **낯선 예약 작업**, **시작 폴더 자동 실행 항목**의 세 패턴을 정리했습니다. 패턴마다 이름, 판단 조건, 한 줄 근거, 공식 참고 링크를 작성했습니다.
- **검증:** 사용자 PC에서 JSON 형식과 **패턴 3개 / 조건 3개 / 한 줄 근거 3개**를 검사했습니다.

| 패턴 | 기술 근거 | 차단 판단에서 주의한 점 |
|---|---|---|
| 서명 없는 신규 서비스 등록·변경 | [T1543](https://attack.mitre.org/techniques/T1543/) | 단순 서비스 재시작·설명 변경만으로 확정하지 않음 |
| 낯선 예약 작업 실행 | [T1053](https://attack.mitre.org/techniques/T1053/) | 수업 중 정상 예약 작업을 자동 차단하지 않음 |
| 시작 폴더 자동 실행 항목 | [T1547.001](https://attack.mitre.org/techniques/T1547/001/) | 단발 변경만으로 자동 차단하지 않음 |

## 제작 3 — 격리 환경의 독립 판단

- **문제:** 심판은 네트워크나 다른 파일에 접근하지 않고 `decide.mjs` **한 파일만** 불러옵니다. 불명확한 변화와 명확한 지속성 공격을 구별해야 합니다.
- **해결:** 세 패턴을 파일 상단 상수로 내장하고 `decide(alert)`가 경보의 설명·MITRE 기술·위험 수준·실행 경로·반복 여부를 교차 확인하도록 했습니다. 반환은 `{ action, confidence, reason }` 세 필드이며, 확신도 **0.85 이상 block / 0.50 이상 alert / 그 미만 record**로 분리했습니다. 파일에 `import`나 파일 입출력은 없습니다.
- **검증:** 사용자 PC에서 문법·반환 형식·독립 실행 제약 및 경보 **24건의 8/8/8 분류**, 정상 이벤트 오차단 **0건**을 확인했습니다. 첫 검증의 한글 문자열 비교 오류는 PowerShell 파이프 인코딩 문제였고 UTF-8 설정 후 모두 통과했습니다.

## 제작 4 — 만료되는 대응 후보와 알림

- **문제:** `block`이라는 분류만으로 실제 접근이 차단되는 것은 아니며, IP 주소를 무조건 차단하면 같은 주소를 쓰는 정상 사용자까지 영향을 받을 수 있습니다.
- **해결:** `respond.mjs`에서 명확한 `block` 판정만 **15분 만료** 거부 후보 규칙으로 구성했습니다. 규칙에 `ruleId`, 시작·만료 시각, `evidenceAlertIds`, 패턴명을 남기고, 동일 IP의 정상·애매한 경보가 섞이면 거부 후보 생성을 보류하도록 했습니다. `block`과 `alert`의 요약은 원본 계정·IP·경로를 싣지 않고 `xdr/alerts.log`에 한 줄씩 누적합니다.
- **검증:** 사용자 PC에서 **거부 후보 8개**, **알림 로그 16줄 추가**, 만료 후 `continue`, 동일 IP 혼합 이벤트 보호, 기존 ZTNA 판정기 로컬 테스트 **4/4 통과**를 확인했습니다.
- **운영 한계:** 공식 ZTNA 요청 계약에는 신뢰된 출발 IP와 외부 규칙 등록 경로가 없어 **`staged_only`**로 후보만 저장했습니다. `checkTrustedSourceIp()`의 `deny`는 신뢰된 IP를 가정한 로컬 연결 시험이며 운영 엔진의 실제 차단은 아닙니다. `continue`는 기존 판정기로 진행한다는 뜻이고 접근 허용을 뜻하지 않습니다.

## 제작 5 — 전체 경보 재시험

- **문제:** 탐지 결과를 저장해 명확한 공격이 차단 후보로 분류되고 정상 경보가 잘못 `block` 되지 않는지 확인해야 합니다.
- **해결:** `npm.cmd run xdr:run -- persistence`를 재실행하고 `xdr/persistence/result.json`에 전체 24건의 판정 결과를 저장했습니다.
- **검증:** `counts = { block: 8, alert: 8, record: 8 }`이며 정상 이벤트 **`ps-17`~`ps-24` 모두 `record`**, 오차단 **0건**을 확인했습니다. 재실행 결과가 이전 파일과 같아 결과 파일 내용은 변경되지 않았고, 저장점은 `README.md`만 별도 커밋했습니다.

- **문제:** 시스템 재시작 후에도 남는 비정상 서비스·예약 작업·시작 폴더 변경을 탐지하면서, 정상 수업 도구와 단발 변경을 오차단하지 않아야 했습니다.

## 재현과 검증 범위

```powershell
node xdr/persistence/read-alerts.mjs | Measure-Object -Line
npm.cmd run xdr:run -- persistence
Get-Content xdr/persistence/result.json -Raw -Encoding UTF8
node xdr/persistence/respond.mjs
npm.cmd run decider:test
```

`respond.mjs` 재실행 시 `xdr/alerts.log`에 동일한 모의 경보에 대한 알림이 **추가 누적**됩니다. `xdr/alerts.log`, `deny-rules.json`은 Git 제외 대상이며, 실제 비밀값과 사용자 자료를 포트폴리오에 보관하지 않습니다. 공식 심판의 **평가 성공**과 실습 코드의 **실제 운영 집행 여부**는 구분합니다.
