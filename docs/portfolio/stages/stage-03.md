# 3단계 | 로그인 기반 메모 API 구성

**기록 출처:** [기존 루트 README — 3단계 저장점](../../../README.md)  
**문장 상태:** 당시 포트폴리오용 3줄 기록 원문을 확인하지 못해, README 검증 사실을 **새로 요약**했습니다.

## 과제 개요

Supabase Auth 로그인·로그아웃과 토큰 검증을 적용하고, 로그인한 사용자가 자신의 UUID 메모를 조회·추가·수정·삭제하도록 구현했습니다.

## 3줄 요약 — 당시 원문 아님

- **문제:** 2단계의 가상 메모 API는 인증 없이 호출할 수 있었고 사용자별 신규 메모를 구분할 수 없었습니다.
- **해결 방법:** Supabase Auth의 이메일·비밀번호 로그인과 서버의 Bearer 토큰 검증을 연결하고, `vault_user_notes`에 UUID·`owner_id` 기반 메모 CRUD를 추가했습니다.
- **검증:** README 기준 A 계정의 로그인·로그아웃·추가·수정·삭제·새로고침 유지, 비로그인 `GET /api/notes`의 HTTP 401, 삭제된 UUID의 인증된 GET HTTP 404를 확인했습니다.

## 확인된 구현

- 서버는 `src/verify-login.mjs`로 토큰을 검증하고 로그인 사용자 ID를 사용했습니다.
- API 허용 경로는 목록과 개별 메모 GET·POST·PUT·DELETE 5개였습니다.
- 기존 실습용 가상 메모 4건은 별도 읽기 전용으로 보존했습니다.

## 한계

이 단계에서는 단건 조회·수정·삭제의 **소유자 검사를 아직 구현하지 않아** 다른 로그인 사용자가 UUID를 알고 접근할 가능성이 남아 있었습니다. A/B 간 교차 접근 차단 시험은 4단계에서 진행했습니다. 공식 심판 판정 결과는 여기서 주장하지 않습니다.
