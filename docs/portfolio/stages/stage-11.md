# 11단계 | 설치 가능한 접속 앱과 승인된 기기 접근 제어

**기록 출처:** 루트 [README의 11단계 포트폴리오 기록](../../../README.md), [기기 승인 운영 절차](../../STAGE11_DEVICE_APPROVAL.md), 관련 코드·테스트, 사용자 제공 공식 평가 결과.

**기록 상태:** 2026-11-04 공식 심판 **100/100점**(조건 6개, 완결성 가점 3개; 사용자 제공 결과). [평가 기준 커밋 `885cb7b8e7c4`](https://github.com/Taetaeeee/choi-bujang-secret-vault/commit/885cb7b8e7c4).

## 과제와 목표

기존 로그인에 성공한 계정이라고 해서 **현재 접속 기기까지 승인된 것은 아닙니다**. 개인 메모 소유권 보호와 기존 ZTNA 판정기 규칙을 유지하면서, 설치 가능한 PWA 접속 앱과 서버 승인 절차를 추가하는 것이 목표였습니다.

## 제작 1 — 설치 가능한 접속 앱

- **문제:** 브라우저에서 앱을 설치했다는 사실을 기기 승인으로 오해하면 보호 자료가 잘못 노출될 수 있음.
- **해결 방법:** `public/manifest.webmanifest`, 192·512px 아이콘, 기기 승인 상태와 오프라인 안내를 제공했습니다. 설치 여부 자체는 승인 근거로 쓰지 않고 개인 메모를 오프라인 캐시에 저장하지 않도록 했습니다.
- **검증:** `test/stage11-pwa.test.mjs`에서 설치 설정·기존 경로 유지·개인 자료 캐시 제외를 검사했습니다. 앱 설치와 실제 승인 여부를 별도로 확인했습니다.

## 제작 2 — 서버 기기 승인과 자료 API 차단

- **문제:** 브라우저가 임의로 보낸 `approved` 상태를 믿거나 로그인 토큰을 웹 저장소에 보관하면 승인 우회 및 토큰 노출 위험이 있음.
- **해결 방법:** `POST /api/device`는 먼저 `pending` 요청만 만들고, 별도 운영자가 승인 테이블의 정확한 요청을 `approved`로 변경하도록 구성했습니다. `api/notes.js`에서 매 자료 조회·생성·수정·삭제 전에 서버 인증·기기 승인·소유권을 검사하도록 했습니다. 로그인 세션은 암호화된 `Secure`·`HttpOnly`·`SameSite=Strict` 쿠키로 취급하고, 기기 식별자는 서버가 발급한 불투명 쿠키의 SHA-256 지문으로 승인 DB에 보관하도록 했습니다.
- **검증:** 사용자 기록상 동일한 시험 계정·브라우저에서 승인 전 `GET /api/notes`는 **HTTP 403 / `DEVICE_NOT_APPROVED`**, 운영자 승인 후 **HTTP 200**과 기존 메모 목록 표시를 확인했습니다. `test/stage11-device.test.mjs`에서는 자가 승인 거부·미승인 접근 차단 등을 로컬 테스트했습니다.

| 운영 기기 승인 후 | 동일 시험 브라우저 `approved`, 자료 API **200** |
| 11단계 관련 로컬 검사 | 사용자 기록 기준 **27/27 통과** |

| 배포·제출 | 단계 11 배포 커밋 일치, 제출 묶음 생성 확인 |

수치는 당시 실행 기록입니다. **이 포트폴리오 문서 작성 과정에서 운영 승인이나 로컬 테스트를 재실행한 것은 아닙니다.**

## 선택한 설계와 배운 점

- **설계 선택:** 앱 설치·로그인·기기 승인을 서로 다른 조건으로 두고, 최종 보호 자료 접근은 브라우저 표시가 아닌 **서버 API**가 결정하도록 했습니다.
- **기여 기록:** 승인 요청 → 관리자 승인 → 승인 상태 재확인 → API 접근의 흐름과 검증을 구현·점검했습니다. 과제 요구로 수행한 작업과 독자적인 아이디어를 구분할 원문 기록이 부족하므로 후자를 임의로 만들어 내지 않습니다.
- **학습:** 인증은 ‘누구인가’, 기기 승인은 ‘이 기기에서 접속해도 되는가’, 소유권 검증은 ‘이 자료에 접근할 권한이 있는가’를 각각 확인합니다. 문제가 있으면 자료를 제공하지 않는 **실패-차단(fail-closed)**이 중요합니다.

## 한계

쿠키에 연결된 기기 승인 기록은 **하드웨어 기기 증명**이 아니며, 쿠키 복제 차단까지 입증하지 않습니다. 다른 기기·시험 계정 B의 운영 교차 접근, 운영 메모 CRUD 전체, 외부 ZTNA 엔진의 `deviceRegistered`와 승인 DB 사이 실시간 연동은 당시 자료에서 직접 실측되지 않았습니다. 공식 100점은 이러한 개별 실측을 모두 대체하지 않습니다.

## 포트폴리오 3줄 요약

- **문제:** 로그인된 계정이라도 미승인 기기에서 보호 자료에 접근할 수 있는 위험을 해결해야 했습니다.
- **해결:** PWA 설치와 권한을 분리하고 서버 기기 승인 상태를 개인 메모 API의 접근 조건으로 연결했습니다.
- **검증:** 운영 시험 브라우저에서 승인 전 **403 → 승인 후 200**, 관련 로컬 검사 **27/27** 및 공식 심판 **100/100점**을 확인했습니다.
