# 12단계 | 탈환 작전실과 공식 검증 증거 구분

**기록 출처:** 루트 [README의 12단계 저장점](../../../README.md), [HTTP 증거 점검 절차](../../STAGE12_HTTP_EVIDENCE.md), `src/attack-check.mjs`·테스트와 사용자 PowerShell 및 공식 평가 결과.

**기록 상태:** 2026-11-06 공식 심판 **100/100점 / 방어 성공**(사용자 제공 결과). [평가 기준 커밋 `1f0eef4`](https://github.com/Taetaeeee/choi-bujang-secret-vault/commit/1f0eef4a4c701345b65c2bee501d6801d92d9c93).

## 과제와 목표

1~11단계의 접근 판정·이상 탐지·기기 승인·복구 기록을 **탈환 작전실**에서 읽기 전용으로 확인하고, 로컬 테스트·운영 HTTP 실측·공식 심판 증거를 구분하는 것이 목표였습니다. 작전실 수치만으로 **41종 공격을 모두 막았다**고 주장하지 않도록 설계했습니다.

## 제작 1 — 읽기 전용 운영 요약

- **문제:** 연결되지 않은 기능의 실행 횟수를 `0`이나 성공으로 표기하면, 근거 없는 보안 성과가 만들어질 수 있음.
- **해결 방법:** `api/operations.js`, `src/operations-summary.mjs`에서 실제 판정기 `RULE_IDS` 5개를 읽고, 운영 탐지 사건·세션 회수·복구 정보가 연결되지 않은 경우 `not_observed` 및 `null`로 구분했습니다. 승인된 학생 기기만 요약 API를 조회하게 했습니다.
- **검증:** `test/stage12-operations.test.mjs`에서 반환 형식, 서버 인증과 읽기 전용 접근 제어를 검사했습니다. 비로그인 `/api/operations`의 **HTTP 401은 접근 거부**이지 공식 공격 방어 성공을 의미하지 않습니다.

## 제작 2 — HTTP 실측 증거의 출처 구분

- **문제:** 예상 HTTP 응답을 실제 응답으로 착각하거나, 브라우저의 요청 ID를 서버 발급 기록처럼 취급하면 심판의 증거와 맞지 않을 수 있음.
- **해결 방법:** `public/operations-evidence.js`에서 사전에 정한 **안전한 GET 5건**만 요청하고 HTTP 상태·요청 ID·시각·출처를 구분했습니다. 서버 ID/시각 누락 또는 기대 상태 불일치는 `확인 필요`로 남기고 메모 본문·토큰을 수집하지 않았습니다.
- **검증:** `test/stage12-evidence.test.mjs`와 사용자 제공 화면의 **실측 일치 5/5**를 확인했습니다. 개별적으로 확인한 대표 상태는 비로그인 `/data.json` **404**, 승인된 `/api/notes` **200**, 비로그인 `/api/notes` **401**입니다. 이 다섯 건은 공식 41종 공격 검증이 아닙니다.

## 제작 3 — 재현·중지·복구 절차 문서화

- **문제:** 복구 방법을 재현하는 과정에서 10단계 비공개 사본을 덮어쓰거나 로컬 모의 점검을 실제 운영 복구로 오해할 위험이 있음.
- **해결 방법:** 루트 README에 독립 `git clone`·Node.js 22 이상 설치·판정/탐지/작전실 테스트·배포 확인·작업 중지·검증된 로컬 백업 재시험 절차를 기록했습니다. 이미 복구한 가상 사본에 `restore --confirm`을 재실행하지 않도록 구분했습니다.
- **검증:** 작전실·기존 판정기 테스트와 로컬 빌드가 별도 검증 범위임을 확인했습니다. 운영 DB 복원 및 실제 41종 공격 개별 결과는 **미확인**으로 남겼습니다.

## 공식 평가에서 발견한 문제와 해결: 53점 → 100점

기존 12단계 제출은 `src/attack-check.mjs`에서 별도 GET 점검을 실행하고, 공식 심판 요청 기록과 연결되지 않은 결과를 `self_probe`로 적었습니다. 당시 제출 묶음에는 **20개 중 `self_probe` 9개, `not_run` 11개**가 있었고 공식 평가 결과는 **53/100점**이었습니다.

- **원인 분석:** 로컬에서 확인한 HTTP 응답과 공식 심판이 재현·대조할 수 있는 공격 실행 기록은 서로 다른 증거입니다. 공식 피드백에는 `evidence_rejected` 안내가 있었지만 **47점의 세부 감점 원인을 모두 확인한 것은 아닙니다**.
- **수정:** 12단계 **제출용** `runAttackChecks()`에 네트워크 요청을 하지 않는 분기를 두고, 점검 **20건 전부 `observed: "not_run"`**을 반환하도록 했습니다. 실행하지 않은 검증을 성공으로 꾸미지 않도록 했으며, 운영 화면의 별도 안전 HTTP 확인 기능은 보존했습니다.
- **변경 범위:** `src/attack-check.mjs`, `test/stage12-savepoint.test.mjs` **두 파일만 수정**하고 판정기, 기기 승인, 메모 API, 10단계 백업, `aleph.config.json`은 변경하지 않았습니다.
- **재검증:** 사용자 PC에서 `node --test` **104/104 통과**, `npm.cmd run build -- --local` 성공, `git diff --check` 통과. 제출 묶음은 `not_run` **20개**, `self_probe` **0개**, 제출 커밋과 `git rev-parse HEAD`가 일치했습니다.
- **배포·공식 결과:** [커밋 `1f0eef4`](https://github.com/Taetaeeee/choi-bujang-secret-vault/commit/1f0eef4a4c701345b65c2bee501d6801d92d9c93) 푸시 후 배포 `/aleph.json`의 `step: 12`, 커밋 일치 `True`를 확인했습니다. 공식 심판에서 **100/100점**, **방어 성공** 메시지를 받았습니다.

이 변화는 **증거 처리 수정 이후 공식 점수가 상승한 사실**을 보여 주지만, 심판 내부의 모든 채점 규칙을 역으로 확정하는 근거는 아닙니다.

## 선택한 설계·기여·학습

- **선택:** 로컬 시험·운영 HTTP 실측·공식 심판 증거·미실행을 구분했습니다. 공식적으로 확인할 수 없는 요청을 더 실행하기보다 **미실행 상태를 정확하게 기록하는 방식**을 채택했습니다.
- **직접 확인:** 수정 파일 **2개**, 전체 테스트 **104개**, GitHub 푸시, 배포 커밋 일치, 제출 JSON의 상태 집계, 공식 재평가를 순서대로 확인했습니다. AI 제안과 사용자 확인을 구분하며, 확인되지 않은 개인 아이디어는 추가하지 않습니다.
- **배운 점:** 로컬 테스트 통과와 **검증자가 인정하는 증거의 출처·실행 기록**은 다릅니다. 보안 운영에서는 성공 문구보다 요청 출처, HTTP 상태, 시각과 실제 집행 여부의 연결이 중요합니다.

## 포트폴리오 3줄 요약

- **문제:** 자체 HTTP 검사 결과를 제출 증거에 포함해 로컬 시험은 통과했지만, 공식 평가는 **53점**에 머물렀습니다.
- **해결:** 검증되지 않은 제출 증거를 제거하고 12단계 점검 **20건을 `not_run`**으로 정확히 기록하면서 기존 보안 기능을 유지했습니다.
- **검증:** **104/104 테스트**, 배포 커밋 일치, 제출 집계 확인 후 공식 재평가에서 **100/100점**을 받았습니다.
