# 8단계 | 자료마다 갈 수 있는 구역을 나눕니다

**기록 출처:** 제작 1~3 공식 요청과 사용자 PowerShell 실행 결과, [8단계 저장점 커밋](https://github.com/Taetaeeee/choi-bujang-secret-vault/commit/98ca7c326a1817a871a1e240402893bd3656da37)

## 과제와 목표

동일 계정으로 로그인했더라도 개인 메모·반 공지·강사 자료를 동일한 권한으로 접근해서는 안 됩니다. 사용자·기기·HTTP 동작·정확한 자원 경로에 따라 접근 후보를 제한하고, 최종 메모 API에서도 서버가 검증한 신원과 DB의 저장 소유자를 다시 확인했습니다. 6~7단계의 기기 등록 및 복합 이상 접속 추가 인증 규칙은 유지했습니다.

## 제작 1 — 개인 메모와 강사 공지의 자원 ID 분리

- **문제:** 개인 메모와 강사 공지의 자원 구분이 모호하면 이후 구역별 권한 규칙을 적용하기 어려움.
- **해결 방법:** `src/resource-id.mjs`에 `personal-note`와 `instructor-notice` 자원 종류를 정의했습니다. 실제 메모 서버 함수 `api/notes.js`는 기존 URL 및 응답 본문을 유지하면서 요청별 `X-Resource-ID` 헤더를 설정합니다. DB 메모 ID·화면 메뉴·데이터를 바꾸지 않았습니다.
- **검증:** `test/resource-id.test.mjs` 3건 통과. 개인 메모 목록/단건 구분, 서로 다른 구역의 ID 충돌 방지, 임의 구역과 위험한 ID 거부를 로컬에서 확인했습니다. 강사 공지는 **식별 규칙만 정의**했으며 공지 데이터·실제 API는 미구현입니다.

## 제작 2 — 서비스·메서드·정확한 경로 기반 구역 판정

- **문제:** 메모 전체 목록, 공지 쓰기, 강사 자료 및 미정의 경로로 접근 범위가 넓어질 위험이 있음.
- **해결 방법:** `src/decider.mjs`에서 엔진이 확인한 `service`, `method`, `path`, `route`를 결합해 개인 메모 **`GET /notes/:id` 단건**과 반 공지 **`GET /notices`, `GET /notices/:id` 읽기**만 허용 후보로 설정했습니다. 메모 목록/쓰기, 공지 쓰기, 강사 자료, 알 수 없는 경로·쿼리 기능·`/notes/export`는 거부하도록 했습니다. 심판 가상 메모 ID에 UUID 형식을 강제하지 않았고, 계약에 없는 `request.role`을 참조하지 않았습니다.
- **검증:** `test/stage8-zones.test.mjs` 7건 통과. 기존 판정기 테스트 4건 통과, `fixture:7`에서 정상 `allow`·복합 이상 `step_up` 유지 확인. `aleph.config.json`의 `allowedRoutes`는 `GET /api/notes/:id`, `GET /api/notices`, `GET /api/notices/:id`로 제한했습니다.

## 제작 3 — 최종 메모 API의 서버 소유권 재확인

- **문제:** 화면이나 판정기 규칙만으로는 사용자가 직접 API 주소를 호출하는 경우의 자료 노출을 막았다고 볼 수 없음.
- **해결 방법:** `api/notes.js`에 기존 로그인 검증과 DB 소유자 조건을 유지하면서 `src/api-resource-access.mjs`의 소유권 검사를 적용했습니다. 목록의 모든 반환 행, 메모 생성 직후 저장 결과, 단건 조회·수정·삭제에서 `owner_id`가 서버 검증 사용자와 일치하는지 재확인합니다. 불일치 메모 단건은 404, 소유자가 섞인 목록은 403으로 처리하고 본문에 포함된 `role`·`owner_id`로 권한을 부여하지 않습니다.
- **검증:** `test/stage8-api-access.test.mjs` 3건 통과. 가상 검증 사용자 본인 메모 허용, 타인 메모 거부, 타인 행 혼입 목록 거부를 확인했습니다. **실제 A/B 계정으로 운영 API를 직접 호출한 실측은 미실행**입니다.

## 결정·학습과 구현 한계

- **설계 범위:** 화면 메뉴 변경과 기존 메모 주소·데이터 변경을 피하면서, 자원 ID 식별 → 판정기 구역 구분 → API 소유자 검사를 제작별로 나눠 적용했습니다.
- **인가 개념:** 로그인 인증과 자료 접근 권한은 다릅니다. 판정기는 정확한 서비스·경로·동작을 검사하고, 메모의 실제 소유자는 최종 API에서 검증하도록 역할을 분리했습니다.
- **강사 권한:** 엔진 요청 계약에 강사 `role`이 없고 운영 서버에도 검증 가능한 강사 권한 저장소·관리 API가 없어 임의로 권한을 만들어 주지 않았습니다. 반 공지 경로는 **판정 정책용 가상 경로**이며 실제 공지 API가 구현된 것은 아닙니다.
- **기존 API와 정책의 차이:** 기존 화면 호환을 위해 서버 `/api/notes` 목록·쓰기 API는 남겨 두었으나, **판정기에서는 목록·쓰기 경로를 허용하지 않습니다.** 서버 API와 엔진 판정기의 실환경 연동 여부는 확인하지 않았습니다.
- **실측 범위:** 공개 배포의 단계·커밋 일치, 제출 묶음 생성과 공식 심판 점수는 확인됐습니다. A/B 계정별 운영 API 직접 요청 및 실제 강사 권한 검증은 미실행으로 남겼습니다.
- **기여 기록:** 제작 조건에 따라 AI와 함께 구현·검증한 내역이며, 외부 요구와 별개로 독자 개발한 새 기능이 있었다고 주장하지 않습니다.
