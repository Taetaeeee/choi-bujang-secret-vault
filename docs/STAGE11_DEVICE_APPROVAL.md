# 11단계 제작 2 — 기기 승인 운영 절차

- 변경 범위: 기존 PWA 화면, `/api/auth`의 HttpOnly 서버 세션 쿠키화, `/api/device` 승인 요청·상태, `/api/notes` 요청당 승인 재검증, 독립된 승인 테이블.
- 기기 승인 **요청**은 로그인된 학생에게 `pending` 레코드를 만들 뿐이며 `approved`로 변경하지 않습니다. 설치·로그인·클라이언트의 status 필드는 승인 근거가 아닙니다.
- 운영자는 별도 인증된 Supabase SQL Editor에서 신청자가 제시한 요청 번호와 실제 사용자 ID를 대조하고, 확인된 한 건만 `pending → approved` 처리합니다. 운영자 승인 권한이 없으면 서버는 계속 잠김 상태를 유지합니다.
- 정적 앱 설치 파일만 공개됩니다. 미승인 계정/기기의 **GET/POST/PUT/DELETE `/api/notes`** 요청은 API 서버에서 HTTP 403으로 차단합니다. 테이블/환경변수 누락 시 HTTP 503으로 실패-차단합니다.
- 사용자 인증 세션은 AES-256-GCM으로 암호화해 `__Host-`·`Secure`·`HttpOnly`·`SameSite=Strict` 쿠키에 넣습니다. Supabase 액세스·갱신 토큰은 `localStorage`, `sessionStorage`, JS 응답에 두지 않습니다. 운영 환경변수 `VAULT_SESSION_KEY`에는 32바이트 암호키의 64자리 hex 문자열이 필요하며 공개 저장소나 채팅에 값을 기록하지 않습니다.
- 승인 신청에 사용되는 별도 HttpOnly 쿠키는 서버가 생성한 무작위 **불투명 식별자**이고, DB에는 그 SHA-256 지문만 기록합니다. 이것은 기기 개인키가 아니며, **쿠키를 다른 기기로 복사했을 때의 하드웨어 수준 기기 복제 차단까지 증명하지는 않습니다.** 실제 하드웨어 바인딩은 WebAuthn/플랫폼 인증기 등 추가 기술이 필요합니다.
- 이 방식은 Supabase의 운영자 승인 테이블과 Vercel 환경변수 설정을 필요로 합니다. SQL Editor에서 `docs/STAGE11_DEVICE_APPROVAL.sql`을 적용한 뒤 Vercel **Settings → Environment Variables**에 `VAULT_SESSION_KEY`를 Production으로 입력하고 재배포합니다. 비밀값은 Git 또는 문의 글에 넣지 않습니다.
- 서버 쪽 승인 결과를 변경할 수 있는 공개 HTTP API는 없습니다. 브라우저의 [승인 요청]은 `pending`만 만들며, [승인 상태 다시 확인]은 서버 조회 결과만 표시합니다.
- 이 단계의 보안 테스트는 로컬 모의 DB 시험과 실제 운영 DB 테스트를 구분합니다. 운영 배포와 실제 운영자 승인 전까지 설치된 앱에서 보호 자료를 열 수 있다고 주장하지 않습니다.

## 수동 확인 순서

1. `node --test test/stage11-device.test.mjs test/stage11-pwa.test.mjs`와 기존 단계 회귀 테스트를 실행합니다. `git diff --check`로 수정 파일을 검증합니다.
2. SQL과 환경변수 적용 전에는 로그인/기기 승인 요청이 `503`을 반환할 수 있습니다. **자료가 열리면 실패**입니다.
3. 운영 설정 후 새 브라우저에서 로그인 → 승인 요청 → 상태 `pending`을 확인합니다. 이때 메모 영역은 숨겨져 있고 GET `/api/notes`는 `403 DEVICE_NOT_APPROVED`여야 합니다.
4. 운영자가 SQL Editor에서 정확히 해당 요청 번호와 소유자 1건을 승인한 뒤, 해당 브라우저에서 상태 재확인을 눌러 `approved`가 반환되는지 봅니다. 승인된 동일 브라우저에서만 기존 메모 화면을 정상적으로 여는지 확인합니다.
5. 새로운 시크릿 창, 다른 계정, 취소된 승인 또는 쿠키 삭제에서는 메모 API가 다시 거부되어야 합니다. 별도 운영 로그와 DB 정책 검증 결과가 없다면 **미실행**으로 남깁니다.
6. 토큰/쿠키 값, 기기 지문 및 실제 메모 본문은 화면 캡처·커밋·제출 기록에서 제외합니다.
